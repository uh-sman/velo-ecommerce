# Performance: the hot-query review

PLANNING.md Phase 14: _review `EXPLAIN ANALYZE` for every hot query; eliminate all N+1 queries with eager loading._ What was measured, what was found, and what changed (2026-10-04).

---

## How it was measured

**Data.** A scratch database (`velo_perf`) migrated to head and loaded with `seed --products 1680` (the most the seed can generate), plus a bulk SQL load for order and worker volume:

| Table                              |          Rows | Table                       |        Rows |
| ---------------------------------- | ------------: | --------------------------- | ----------: |
| products                           |         1,680 | orders                      |       6,003 |
| product_variants / inventory_items |        19,680 | order_items                 |      12,007 |
| variant_option_values              |        38,400 | returns / refunds           |   400 / 300 |
| product_media                      |         4,560 | checkout_sessions           |       6,003 |
| users                              |         2,002 | inventory_reservations      |      12,000 |
| carts / cart_items                 | 8,003 / 8,000 | outbox_events (unpublished) | 30,000 (20) |

Postgres 16 in the dev container, `VACUUM ANALYZE`d after loading, on a WSL2 laptop.

**Query counts.** A harness drives the real app in process (ASGI, lifespan running, sandbox payments, catalog cache off, Meilisearch unreachable so search takes the Postgres fallback) and counts statements per request with a `before_cursor_execute` listener. Transaction control (`SAVEPOINT`, `COMMIT`, …) is not counted.

**Plans.** Every `SELECT` the harness captured was re-run under `EXPLAIN (ANALYZE, BUFFERS)` with its own parameters. The times below are server-side planning + execution, `EXPLAIN (ANALYZE, TIMING OFF)`, median of 7 runs: _before_ is the old SQL on the schema at 0017, _after_ the new SQL at 0018. Wall-clock request times on this machine vary by ±50% run to run, so they are not quoted.

**Kept honest by** `tests/integration/test_query_counts.py`: the same request over a small and a larger data set must issue the same number of statements.

## N+1 queries found and fixed

| Request                                         | Queries before → after | Cause                                                                                                                                  | Fix                                                                                                                                                                                   |
| ----------------------------------------------- | ---------------------: | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/orders` (account, 20 orders)       |             **21 → 2** | `OrderReader._summary` loaded every order's lines to count its units                                                                   | `OrderRepository.unit_counts(order_ids)`: one `GROUP BY` for the page                                                                                                                 |
| `GET /api/v1/admin/orders` (50 orders)          |             **52 → 3** | the same                                                                                                                               | the same                                                                                                                                                                              |
| `GET /api/v1/admin/returns` (50 returns)        |            **102 → 4** | one query per return for its lines, and one per return for its order                                                                   | `OrderRepository._returns(rows)` reads every return's lines in one query; `get_many(order_ids)` reads the orders                                                                      |
| `GET /api/v1/admin/products/{id}` (15 variants) |             **23 → 9** | `InventoryService.stock()` once per variant                                                                                            | `InventoryService.stocks(variant_ids)`                                                                                                                                                |
| `GET /orders/{n}`, `GET /admin/orders/{id}`     |  15 → 15 (bounded now) | one query per parcel for its lines, per return for its lines, per refund for its lines                                                 | `_with_items`, `_returns`, `_refunds`: one query per kind, whatever the count. 15 at one parcel; it no longer grows                                                                   |
| `POST /api/v1/checkout` (5 lines)               |            **26 → 18** | per line: `INSERT` a reservation, `UPDATE quantity_reserved`                                                                           | one multi-row `INSERT`, one `UPDATE … FROM (VALUES …)`. Fewer round trips while the stock rows are locked                                                                             |
| worker: paid event → order (5 lines)            |            **55 → 27** | per line: stock `UPDATE`, ledger `INSERT`, variant label `SELECT`, outbox `INSERT`, order line `INSERT`, cart line `DELETE` + `UPDATE` | `update_many` (`UPDATE … FROM (VALUES …) RETURNING`), `add_movements`, `variant_labels`, `CartRepository.reduce` as two statements; and the ORM now batches multi-row flushes (below) |
| worker: release a checkout (sweeper, abandon)   |              N + 4 → 5 | `add_reserved` once per reservation                                                                                                    | `add_reserved_many`                                                                                                                                                                   |
| worker: outbox relay, 100 product events        |            **100 → 1** | `_slugs_for` read each product by id                                                                                                   | `CatalogRepository.slugs(product_ids)`                                                                                                                                                |

**Multi-row ORM flushes.** Every model has `eager_defaults=True`, so an `INSERT` must `RETURNING` its server defaults. SQLAlchemy batches that into one statement only when it has a _sentinel_ column to match returned rows to objects; our client-generated UUIDv7 key did not qualify because it also has a server default. `HasId.id` is now marked `insert_sentinel=True` (`velo/db/base.py`): five order lines, or five outbox events, are one `INSERT`, not five. This is Python-side only; the schema is unchanged.

Already batched, no change needed: product detail (8 queries, fixed), listing images (`DISTINCT ON`), cart read (8), variant option values, search result cards.

## Plans: what `EXPLAIN ANALYZE` showed

### Catalog

| Request                                                              | Before                                                                                                                                                           | After                                                                                             | Action                                                                                                      |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `GET /products` (newest)                                             | **39 ms**. Seq scans of `products`, `product_variants`, `inventory_items`: every variant in the catalog aggregated for one page                                  | **1.6 ms**. Index scan `idx_products_active`, then `idx_variants_product` per product on the page | Variant stats as a `LATERAL` subquery per product: the work stops with the page                             |
| `GET /products?category=bags` (newest)                               | 45 ms, same seq scans                                                                                                                                            | 1.3 ms, same index path                                                                           | Same; category ids resolved once (`= ANY(ARRAY(…))`) so `idx_products_category`/`idx_products_active` apply |
| `GET /products?collection=…&sort=rating`                             | 36 ms                                                                                                                                                            | 2.9 ms                                                                                            | Price/rating sorts aggregate only the candidate products' variants (`product_id IN (…filters…)`)            |
| `GET /products?brand=…&min_price&max_price&in_stock`                 | 41 ms                                                                                                                                                            | 2.3 ms                                                                                            | `LATERAL` (newest)                                                                                          |
| `GET /products?category=tops&sort=price` (455 products)              | 37–45 ms                                                                                                                                                         | 26–35 ms                                                                                          | Candidate-restricted aggregate                                                                              |
| `GET /products?category=apparel&sort=-price` (908 products)          | 40 ms                                                                                                                                                            | 38–58 ms (noise)                                                                                  | None effective: a price sort needs every candidate's minimum price                                          |
| `GET /products?sort=price` (whole catalog)                           | 42–45 ms                                                                                                                                                         | 44–54 ms (noise)                                                                                  | As above                                                                                                    |
| `GET /products/{slug}/related` (908 candidates, in stock, by rating) | 41 ms                                                                                                                                                            | 47 ms                                                                                             | As above. Not cached; see _Not done_                                                                        |
| `GET /search?q=` fallback: text match                                | **91 ms**. `idx_products_active` with `to_tsvector()` computed per live product, because the FTS match was OR'd with `ILIKE`                                     | **2.1 ms**. Bitmap scan of `idx_products_fts` once, as a hashed subplan                           | `_text_match`: `id IN (SELECT … WHERE fts @@ q) OR title ILIKE …`                                           |
| `GET /search?q=` fallback: option facets                             | **48 ms** (112 matches); 418 ms when every product matches. Seq scans of `option_values` (10,800) and `product_options`, then all 38,400 `variant_option_values` | **9.8 ms**; 127 ms                                                                                | Redundant `product_options.product_id = ANY(ids)`: the planner starts from the matched products' options    |
| `GET /search/suggest`, `GET /products/{slug}`, `/categories`         | < 3 ms, index scans                                                                                                                                              | unchanged                                                                                         | None                                                                                                        |

How the listing chooses: `CatalogRepository._listing(per_product=…)`. Newest-first pages and explicit id lists (search cards, admin list prices) use the `LATERAL`; price and rating sorts, counts and stock filters over a full candidate set use one `GROUP BY`. Measured both ways for every sort above: the `LATERAL` costs a probe per product, so it loses (2×) when every candidate must be aggregated anyway.

## Migration 0018

| Index                 | Change                                                                                                                       | Before → after                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `idx_orders_placed`   | new: `orders (placed_at DESC, id DESC)`                                                                                      | 3.8 ms → 0.18 ms at 6k orders; the old cost grows with the table, the new one does not |
| `idx_checkout_expiry` | predicate `status NOT IN ('confirmed','failed','expired')` → `status IN ('initiated','address_set','shipping_set','failed')` | 3.3 ms → 0.22 ms at 6k sessions; sessions are never purged                             |

`alembic upgrade head`, `downgrade -1` and `upgrade head` again were run against the loaded database; the models declare both indexes, so `test_models_match_the_migrations_exactly` holds.

No index was added where the plan did not ask for one: every other hot query already reads through a primary key, a unique key, or an existing partial index.

## Not done, and why

- **Price and rating sorts over a broad category** (`related` on every product page, ~45 ms) aggregate every candidate's variants. The fix is a denormalised `price_min` / `in_stock` on `products`, kept in step from the inventory and catalog write paths, which is a schema change of its own. Until then, `related` is worth putting behind the catalog cache.
- **`PATCH /checkout/{id}/shipping`** reads the same address three times (16 queries, fixed count). Harmless; not an N+1.
- **GIN pending list.** After a bulk load, `idx_products_fts` answered in 90 ms until `VACUUM` merged its pending list (then 0.03 ms). Autovacuum does this in normal running; after a large import, run `VACUUM ANALYZE products`.
