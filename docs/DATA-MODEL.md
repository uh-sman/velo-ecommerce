# Data Model

PostgreSQL 16. The schema is the contract; everything else is negotiable.

---

## 1. Conventions

| Convention           | Rule                                            | Why                                                                                                                                                     |
| -------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Primary keys**     | `UUID` (v7)                                     | Sequential integers leak order volume to competitors and enable enumeration. UUIDv7 is time-sortable, so unlike v4 it does not destroy B-tree locality. |
| **Money**            | `BIGINT` minor units + `CHAR(3)` currency       | Exact integer arithmetic. `2999` + `USD` = $29.99. **No float, ever.**                                                                                  |
| **Timestamps**       | `TIMESTAMPTZ`, always UTC                       | Naive timestamps are a latent bug in every system that outlives one DST change.                                                                         |
| **Soft delete**      | `deleted_at TIMESTAMPTZ NULL` on catalog only   | Orders and payments are **never** soft-deleted. Financial records are immutable.                                                                        |
| **Status columns**   | `TEXT` + `CHECK` constraint                     | Postgres enums require a migration to extend and cannot be reordered. A CHECK constraint gives the same safety with none of the pain.                   |
| **Naming**           | `snake_case`, plural tables, `<table>_id` FKs   | Predictable; autogenerated migrations stay readable.                                                                                                    |
| **Audit columns**    | `created_at`, `updated_at` on every table       | Non-negotiable for debugging anything.                                                                                                                  |
| **Constraint names** | `pk_`, `fk_`, `uq_`, `ix_`, `ck_<table>_<name>` | Set by the SQLAlchemy naming convention in `velo/db/base.py`, so migrations can drop and alter by name. Indexes named below keep their names.           |

### Where this lives in code

The SQL in this document is the contract; the SQLAlchemy models in `apps/api/velo/domains/<domain>/models.py` implement it, and the Alembic migrations in `apps/api/migrations/versions/` create it. `tests/integration/test_migrations.py` fails if the models and the migrated database disagree in any column, type, default, index, or constraint, so drift between the two cannot merge.

**`uuidv7()`.** Postgres 16 has no UUIDv7 function (it arrives in Postgres 18). The application generates keys itself (`velo/db/ids.py`), and migration `0001` defines a SQL `uuidv7()` so the `DEFAULT uuidv7()` below also works for rows inserted outside the ORM.

**Stricter than the SQL below in one respect:** every money column on `orders` and `order_items` also carries a `>= 0` CHECK, including the discount, shipping, and tax amounts the SQL leaves unconstrained. A negative tax is never valid, and the balance equation alone would accept one.

### The money rule

```python
# WRONG — this will eventually cost real money
price = 29.99                    # 29.989999999999998

# RIGHT
price_amount   = 2999            # BIGINT, minor units
price_currency = "USD"           # ISO 4217
```

Floating point is binary; 0.01 has no exact binary representation. Sum enough line items and the total drifts from the sum of its parts, which is exactly the class of bug an auditor finds and you cannot explain. `BIGINT` cents is how payment processors themselves represent money — Stripe's API takes integer minor units for precisely this reason.

`NUMERIC` is used only where a value is genuinely fractional and not a currency amount: tax **rates**, weights, and dimensions.

## 3. Identity

Roles are a column rather than `roles`/`permissions` tables: the five roles are fixed, and the permissions each one grants are mapped in code (Phase 5), where they are reviewed and tested like any other rule. A "session" in the account UI is one refresh-token family (ADR-008), so there is no separate `sessions` table.

```sql
CREATE TABLE users (
    id                  UUID PRIMARY KEY DEFAULT uuidv7(),
    email               CITEXT NOT NULL UNIQUE,      -- CITEXT: case-insensitive, no LOWER() indexes needed
    password_hash       TEXT,                        -- NULL for OAuth-only accounts
    first_name          TEXT,
    last_name           TEXT,
    phone               TEXT,
    email_verified_at   TIMESTAMPTZ,
    role                TEXT NOT NULL DEFAULT 'customer'
                        CHECK (role IN ('customer','fulfilment','staff','admin','owner')),
    status              TEXT NOT NULL DEFAULT 'active'
                        CHECK (status IN ('active','suspended','deleted')),
    failed_login_count  INT  NOT NULL DEFAULT 0,
    locked_until        TIMESTAMPTZ,
    marketing_opt_in    BOOLEAN NOT NULL DEFAULT FALSE,
    metadata            JSONB NOT NULL DEFAULT '{}',
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_users_email_active ON users (email) WHERE status = 'active';

CREATE TABLE refresh_tokens (
    id           UUID PRIMARY KEY DEFAULT uuidv7(),
    user_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash   TEXT NOT NULL UNIQUE,               -- store the hash, never the token
    family_id    UUID NOT NULL,                      -- rotation lineage
    used_at      TIMESTAMPTZ,                        -- non-NULL + presented again = theft
    revoked_at   TIMESTAMPTZ,
    expires_at   TIMESTAMPTZ NOT NULL,
    user_agent   TEXT,
    ip_address   INET,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_refresh_active ON refresh_tokens (user_id)
    WHERE revoked_at IS NULL AND used_at IS NULL;
CREATE INDEX idx_refresh_family ON refresh_tokens (family_id);

CREATE TABLE addresses (
    id             UUID PRIMARY KEY DEFAULT uuidv7(),
    user_id        UUID REFERENCES users(id) ON DELETE CASCADE,  -- NULL = guest checkout address
    label          TEXT,
    first_name     TEXT NOT NULL,
    last_name      TEXT NOT NULL,
    company        TEXT,
    line1          TEXT NOT NULL,
    line2          TEXT,
    city           TEXT NOT NULL,
    region         TEXT,
    postal_code    TEXT,
    country_code   CHAR(2) NOT NULL,
    phone          TEXT,
    is_default_shipping BOOLEAN NOT NULL DEFAULT FALSE,
    is_default_billing  BOOLEAN NOT NULL DEFAULT FALSE,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_addresses_user ON addresses (user_id);
-- At most one default of each kind per user:
CREATE UNIQUE INDEX uq_default_shipping ON addresses (user_id)
    WHERE is_default_shipping AND user_id IS NOT NULL;
CREATE UNIQUE INDEX uq_default_billing  ON addresses (user_id)
    WHERE is_default_billing  AND user_id IS NOT NULL;
```

**`token_hash`, not `token`.** A database dump must not hand an attacker working sessions. Same reasoning as password hashing.

## 4. Catalog

```sql
CREATE TABLE products (
    id               UUID PRIMARY KEY DEFAULT uuidv7(),
    slug             TEXT NOT NULL UNIQUE,
    title            TEXT NOT NULL,
    subtitle         TEXT,
    description      TEXT,
    brand            TEXT,
    status           TEXT NOT NULL DEFAULT 'draft'
                     CHECK (status IN ('draft','active','archived')),
    category_id      UUID REFERENCES categories(id) ON DELETE SET NULL,
    seo_title        TEXT,
    seo_description  TEXT,
    attributes       JSONB NOT NULL DEFAULT '{}',   -- material, care, dimensions, etc.
    rating_average   NUMERIC(3,2),                  -- denormalised, recomputed on review write
    rating_count     INT NOT NULL DEFAULT 0,
    published_at     TIMESTAMPTZ,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

CREATE INDEX idx_products_active   ON products (published_at DESC)
    WHERE status = 'active' AND deleted_at IS NULL;

    WHERE status = 'active' AND deleted_at IS NULL;
CREATE INDEX idx_products_attrs    ON products USING GIN (attributes);
CREATE INDEX idx_products_fts      ON products USING GIN (
    to_tsvector('english', title || ' ' || coalesce(description,''))
);  -- Meilisearch fallback

CREATE TABLE product_variants (
    id                   UUID PRIMARY KEY DEFAULT uuidv7(),
    product_id           UUID NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    sku                  TEXT NOT NULL UNIQUE,
    title                TEXT NOT NULL,             -- "Large / Navy"
    price_amount         BIGINT NOT NULL CHECK (price_amount >= 0),
    price_currency       CHAR(3) NOT NULL DEFAULT 'USD',
    compare_at_amount    BIGINT CHECK (compare_at_amount >= 0),
    cost_amount          BIGINT CHECK (cost_amount >= 0),   -- for margin reporting
    weight_grams         INT CHECK (weight_grams >= 0),
    barcode              TEXT,
    requires_shipping    BOOLEAN NOT NULL DEFAULT TRUE,
    is_taxable           BOOLEAN NOT NULL DEFAULT TRUE,
    position             INT NOT NULL DEFAULT 0,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at           TIMESTAMPTZ,
    CONSTRAINT compare_at_gt_price
        CHECK (compare_at_amount IS NULL OR compare_at_amount > price_amount)
);
CREATE INDEX idx_variants_product ON product_variants (product_id) WHERE deleted_at IS NULL;

-- Option matrix: Size × Colour → variant
CREATE TABLE product_options (
    id          UUID PRIMARY KEY DEFAULT uuidv7(),
    product_id  UUID NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    name        TEXT NOT NULL,                      -- 'Size'
    position    INT  NOT NULL DEFAULT 0,
    UNIQUE (product_id, name)
);

CREATE TABLE option_values (
    id          UUID PRIMARY KEY DEFAULT uuidv7(),
    option_id   UUID NOT NULL REFERENCES product_options(id) ON DELETE CASCADE,
    value       TEXT NOT NULL,                      -- 'Large'
    swatch_hex  TEXT,                               -- for colour swatches
    position    INT  NOT NULL DEFAULT 0,
    UNIQUE (option_id, value)
);

CREATE TABLE variant_option_values (
    variant_id       UUID NOT NULL REFERENCES product_variants(id) ON DELETE CASCADE,
    option_value_id  UUID NOT NULL REFERENCES option_values(id)    ON DELETE CASCADE,
    PRIMARY KEY (variant_id, option_value_id)
);
-- Colour and size filters look variants up by value: the reverse of the key's order.
CREATE INDEX idx_variant_option_values_value ON variant_option_values (option_value_id);

CREATE TABLE categories (
    id          UUID PRIMARY KEY DEFAULT uuidv7(),
    parent_id   UUID REFERENCES categories(id) ON DELETE CASCADE,
    slug        TEXT NOT NULL UNIQUE,
    name        TEXT NOT NULL,
    path        LTREE NOT NULL,        -- 'apparel.tops.tshirts' — whole subtree in one query
    position    INT  NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_categories_path ON categories USING GIST (path);

CREATE TABLE collections (
    id           UUID PRIMARY KEY DEFAULT uuidv7(),
    slug         TEXT NOT NULL UNIQUE,
    title        TEXT NOT NULL,
    description  TEXT,
    rules        JSONB,                 -- NULL = manual; non-NULL = smart collection
    is_active    BOOLEAN NOT NULL DEFAULT TRUE,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE product_collections (
    product_id     UUID NOT NULL REFERENCES products(id)    ON DELETE CASCADE,
    collection_id  UUID NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
    position       INT  NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id, collection_id)
);

CREATE TABLE product_media (
    id          UUID PRIMARY KEY DEFAULT uuidv7(),
    product_id  UUID NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    variant_id  UUID REFERENCES product_variants(id) ON DELETE SET NULL,
    url         TEXT NOT NULL,
    alt_text    TEXT,                   -- required for WCAG; enforced in the admin UI
    width       INT,
    height      INT,                    -- stored so the frontend can reserve space and avoid CLS
    blurhash    TEXT,
    media_type  TEXT NOT NULL DEFAULT 'image' CHECK (media_type IN ('image','video')),
    position    INT  NOT NULL DEFAULT 0,
    renditions  JSONB NOT NULL DEFAULT '[]'  -- resized AVIF/WebP copies: [{width, height, format, url}]
);
CREATE INDEX idx_media_product ON product_media (product_id, position);

CREATE TABLE reviews (
    id                UUID PRIMARY KEY DEFAULT uuidv7(),
    product_id        UUID NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    user_id           UUID REFERENCES users(id) ON DELETE SET NULL,
    order_id          UUID REFERENCES orders(id) ON DELETE SET NULL,  -- verified purchase
    rating            SMALLINT NOT NULL CHECK (rating BETWEEN 1 AND 5),
    title             TEXT,
    body              TEXT,
    status            TEXT NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','approved','rejected')),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_reviews_product ON reviews (product_id, created_at DESC) WHERE status = 'approved';
CREATE UNIQUE INDEX uq_review_per_order_product ON reviews (user_id, product_id, order_id)
    WHERE user_id IS NOT NULL AND order_id IS NOT NULL;
```

**Why `width` and `height` are stored:** the frontend needs intrinsic dimensions to reserve layout space before the image loads. Without them, images pop in and shift the page — Cumulative Layout Shift, a Core Web Vitals failure and a genuinely bad experience on mobile.

## 5. Inventory — the oversell guard

```sql
CREATE TABLE inventory_items (
    id                  UUID PRIMARY KEY DEFAULT uuidv7(),
    variant_id          UUID NOT NULL UNIQUE REFERENCES product_variants(id) ON DELETE CASCADE,
    quantity_on_hand    INT NOT NULL DEFAULT 0 CHECK (quantity_on_hand >= 0),
    quantity_reserved   INT NOT NULL DEFAULT 0 CHECK (quantity_reserved >= 0),
    reorder_point       INT NOT NULL DEFAULT 0,
    track_inventory     BOOLEAN NOT NULL DEFAULT TRUE,
    allow_backorder     BOOLEAN NOT NULL DEFAULT FALSE,
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),

    -- The single most important constraint in this schema.
    -- Even if every line of application code is wrong, the database will not oversell.
    CONSTRAINT reserved_within_stock CHECK (quantity_reserved <= quantity_on_hand)
);
CREATE INDEX idx_inventory_low ON inventory_items (variant_id)
    WHERE quantity_on_hand <= reorder_point;

-- Append-only ledger. Never UPDATE, never DELETE.
CREATE TABLE inventory_movements (
    id              UUID PRIMARY KEY DEFAULT uuidv7(),
    variant_id      UUID NOT NULL REFERENCES product_variants(id),
    quantity_delta  INT  NOT NULL,          -- signed: -1 sale, +1 return, +50 restock
    reason          TEXT NOT NULL CHECK (reason IN
                      ('sale','return','restock','adjustment','damage','theft','initial')),
    reference_type  TEXT,                   -- 'order', 'return', 'manual'
    reference_id    UUID,
    actor_id        UUID REFERENCES users(id),
    note            TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_movements_variant ON inventory_movements (variant_id, created_at DESC);
CREATE INDEX idx_movements_ref     ON inventory_movements (reference_type, reference_id);

CREATE TABLE inventory_reservations (
    id                   UUID PRIMARY KEY DEFAULT uuidv7(),
    variant_id           UUID NOT NULL REFERENCES product_variants(id) ON DELETE CASCADE,
    checkout_session_id  UUID NOT NULL REFERENCES checkout_sessions(id) ON DELETE CASCADE,
    quantity             INT  NOT NULL CHECK (quantity > 0),
    status               TEXT NOT NULL DEFAULT 'active'
                         CHECK (status IN ('active','committed','released','expired')),
    expires_at           TIMESTAMPTZ NOT NULL,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_reservations_expiry ON inventory_reservations (expires_at)
    WHERE status = 'active';   -- the sweeper's index
CREATE INDEX idx_reservations_session ON inventory_reservations (checkout_session_id);

-- "Email me when it is back." One pending request per variant and address;
-- the row is kept once notified, as a record of what was sent.
CREATE TABLE back_in_stock_subscriptions (
    id          UUID PRIMARY KEY DEFAULT uuidv7(),
    variant_id  UUID NOT NULL REFERENCES product_variants(id) ON DELETE CASCADE,
    email       CITEXT NOT NULL,
    user_id     UUID REFERENCES users(id) ON DELETE SET NULL,
    notified_at TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_back_in_stock_pending ON back_in_stock_subscriptions (variant_id, email)
    WHERE notified_at IS NULL;
```

**Available-to-sell is never stored.** It is `quantity_on_hand - quantity_reserved`, computed at read time. A stored derived value is a stored opportunity to be wrong.

### The reservation transaction

```sql
BEGIN;
  SELECT quantity_on_hand, quantity_reserved
    FROM inventory_items
   WHERE variant_id = $1
     FOR UPDATE;                      -- concurrent checkouts on this SKU serialise here

  -- application checks: (on_hand - reserved) >= requested, else abort with OutOfStock

  INSERT INTO inventory_reservations (variant_id, checkout_session_id, quantity, expires_at)
  VALUES ($1, $2, $3, now() + interval '30 minutes');

  UPDATE inventory_items
     SET quantity_reserved = quantity_reserved + $3,
         updated_at = now()
   WHERE variant_id = $1;             -- CHECK constraint is the final backstop
COMMIT;
```

On payment success the reservation is committed: `quantity_on_hand` decrements, `quantity_reserved` decrements, and a `sale` movement is written — all in the same transaction as order creation. On expiry or failure the sweeper releases it: `quantity_reserved` decrements only.

## 6. Cart

```sql
CREATE TABLE carts (
    id            UUID PRIMARY KEY DEFAULT uuidv7(),
    user_id       UUID REFERENCES users(id) ON DELETE CASCADE,
    guest_token   TEXT UNIQUE,            -- opaque, cookie-bound; NULL once claimed by a user
    currency      CHAR(3) NOT NULL DEFAULT 'USD',
    status        TEXT NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active','converted','abandoned','merged')),
    abandoned_at  TIMESTAMPTZ,
    expires_at    TIMESTAMPTZ NOT NULL DEFAULT (now() + interval '30 days'),
    discount_code CITEXT,                 -- the code the customer applied; kept while it does not apply
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT cart_has_owner CHECK (user_id IS NOT NULL OR guest_token IS NOT NULL)
);
CREATE UNIQUE INDEX uq_active_user_cart ON carts (user_id)
    WHERE status = 'active' AND user_id IS NOT NULL;   -- one active cart per user
CREATE INDEX idx_carts_abandoned ON carts (abandoned_at) WHERE status = 'abandoned';

CREATE TABLE cart_items (
    id          UUID PRIMARY KEY DEFAULT uuidv7(),
    cart_id     UUID NOT NULL REFERENCES carts(id) ON DELETE CASCADE,
    variant_id  UUID NOT NULL REFERENCES product_variants(id) ON DELETE CASCADE,
    quantity    INT  NOT NULL CHECK (quantity > 0 AND quantity <= 999),
    seen_price_amount BIGINT,           -- last price shown, for "price changed" warnings only
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (cart_id, variant_id)        -- one row per variant; changes are quantity changes
);
```

**Note what `cart_items` does not contain: a price it charges.** `seen_price_amount` records what the customer was last shown, so a change can be flagged; it is never charged. A cart holds intent — _this variant, this many_. The price is looked up from `product_variants` on every read and every mutation. There is no cached price to go stale and no client-supplied price to tamper with.

The `UNIQUE (cart_id, variant_id)` constraint turns "add to cart" into an upsert, which makes double-clicking "Add" increment a quantity rather than create a duplicate line.

## 7. Checkout & orders

```sql
CREATE TABLE checkout_sessions (
    id                   UUID PRIMARY KEY DEFAULT uuidv7(),
    cart_id              UUID NOT NULL REFERENCES carts(id),
    user_id              UUID REFERENCES users(id),
    email                CITEXT NOT NULL,
    status               TEXT NOT NULL DEFAULT 'initiated' CHECK (status IN
                           ('initiated','address_set','shipping_set',
                            'payment_pending','confirmed','failed','expired','abandoned')),
    shipping_address_id  UUID REFERENCES addresses(id),
    billing_address_id   UUID REFERENCES addresses(id),
    shipping_rate_id     UUID REFERENCES shipping_rates(id),
    discount_id          UUID REFERENCES discounts(id),

    -- Priced snapshot. Recomputed on every mutation, and again before capture.
    currency             CHAR(3)  NOT NULL DEFAULT 'USD',
    subtotal_amount      BIGINT   NOT NULL DEFAULT 0 CHECK (subtotal_amount >= 0),
    discount_amount      BIGINT   NOT NULL DEFAULT 0 CHECK (discount_amount >= 0),
    shipping_amount      BIGINT   NOT NULL DEFAULT 0 CHECK (shipping_amount >= 0),
    tax_amount           BIGINT   NOT NULL DEFAULT 0 CHECK (tax_amount      >= 0),
    total_amount         BIGINT   NOT NULL DEFAULT 0 CHECK (total_amount    >= 0),

    expires_at           TIMESTAMPTZ NOT NULL DEFAULT (now() + interval '30 minutes'),
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT totals_balance CHECK (
        total_amount = subtotal_amount - discount_amount + shipping_amount + tax_amount
    ),
    CONSTRAINT discount_within_subtotal CHECK (discount_amount <= subtotal_amount)
);
CREATE INDEX idx_checkout_expiry ON checkout_sessions (expires_at)
    WHERE status NOT IN ('confirmed','failed','expired');

CREATE TABLE orders (
    id                   UUID PRIMARY KEY DEFAULT uuidv7(),
    order_number         TEXT NOT NULL UNIQUE,      -- 'VLO-7K3M9Q' — not enumerable
    user_id              UUID REFERENCES users(id) ON DELETE SET NULL,
    email                CITEXT NOT NULL,
    checkout_session_id  UUID UNIQUE REFERENCES checkout_sessions(id),  -- one order per session

    status               TEXT NOT NULL DEFAULT 'pending' CHECK (status IN
                           ('pending','paid','processing','partially_fulfilled',
                            'fulfilled','delivered','cancelled','refunded','partially_refunded')),
    payment_status       TEXT NOT NULL DEFAULT 'pending' CHECK (payment_status IN
                           ('pending','authorised','paid','partially_refunded','refunded','failed')),
    fulfilment_status    TEXT NOT NULL DEFAULT 'unfulfilled' CHECK (fulfilment_status IN
                           ('unfulfilled','partially_fulfilled','fulfilled','returned')),

    currency             CHAR(3) NOT NULL,
    subtotal_amount      BIGINT  NOT NULL CHECK (subtotal_amount >= 0),
    discount_amount      BIGINT  NOT NULL DEFAULT 0,
    shipping_amount      BIGINT  NOT NULL DEFAULT 0,
    tax_amount           BIGINT  NOT NULL DEFAULT 0,
    total_amount         BIGINT  NOT NULL CHECK (total_amount >= 0),
    refunded_amount      BIGINT  NOT NULL DEFAULT 0 CHECK (refunded_amount >= 0),

    -- Address SNAPSHOTS, not foreign keys. A customer editing their address book
    -- must never rewrite where a historical order was shipped.
    shipping_address     JSONB NOT NULL,
    billing_address      JSONB NOT NULL,

    discount_code        TEXT,
    customer_note        TEXT,
    internal_note        TEXT,
    metadata             JSONB NOT NULL DEFAULT '{}',
    placed_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    cancelled_at         TIMESTAMPTZ,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT order_totals_balance CHECK (
        total_amount = subtotal_amount - discount_amount + shipping_amount + tax_amount
    ),
    CONSTRAINT refund_within_total CHECK (refunded_amount <= total_amount)
);
CREATE INDEX idx_orders_user        ON orders (user_id, placed_at DESC);
```

### Why order data is snapshotted

This is the single most common data-modelling mistake in e-commerce, so it is worth being explicit.

If `order_items` stored only `variant_id` and joined to `product_variants` for the title and price, then:

- An admin corrects a typo in a product title → every historical invoice changes.
- A seasonal sale drops a price → last month's revenue report silently shrinks.
- A discontinued variant is deleted → historical orders reference nothing.

An order is a **record of an agreement made at a point in time**. It must be immutable against later catalog edits. So `order_items` carries `product_title`, `variant_title`, `sku`, `unit_price_amount`, `tax_rate`, and `image_url` as data, with `variant_id` kept only as a nullable convenience link for reporting.

The same reasoning applies to `orders.shipping_address` and `billing_address` being JSONB snapshots rather than foreign keys into `addresses`.

## 11. Index strategy

Every index below exists to serve a named query. An index with no query is write overhead with no payoff.

| Query                                       | Index                                                     |
| ------------------------------------------- | --------------------------------------------------------- |
| Active products in a category, newest first | `idx_products_category` (partial: active, not deleted)    |
| Product by slug                             | `uq_products_slug` (unique)                               |
| Variants of a product                       | `idx_variants_product` (partial: not deleted)             |
| Low-stock report                            | `idx_inventory_low` (partial: at or below reorder point)  |
| Reservation sweeper                         | `idx_reservations_expiry` (partial: active only)          |
| Customer order history                      | `idx_orders_user`                                         |
| Guest order lookup by email                 | `idx_orders_email`                                        |
| Fulfilment queue                            | `idx_orders_unfulfilled` (partial: paid + unfulfilled)    |
| Payment reconciliation                      | `idx_payments_pending` (partial: non-terminal only)       |
| Webhook deduplication                       | `payment_events (provider, provider_event_id)` unique     |
| Outbox relay                                | `idx_outbox_unpublished` (partial: unpublished only)      |
| Discount code validation                    | `idx_discounts_active` (partial: active; window in query) |

**Partial indexes are used aggressively.** `idx_orders_unfulfilled` indexes only paid-and-unfulfilled orders — typically a few hundred rows out of millions. The index stays in memory, the scan is instant, and it costs almost nothing to maintain because the vast majority of orders never match the predicate.

**Review discipline:** any PR that adds a query runs `EXPLAIN ANALYZE` and pastes the plan into the description. A sequential scan on a table expected to exceed 10,000 rows blocks the merge.

## 12. Partitioning (deferred until needed)

`orders` and `order_events` are the tables that grow without bound. Neither needs partitioning before roughly 50 million rows, but the schema is designed so that partitioning later is a migration rather than a redesign — `placed_at` is `NOT NULL` and is a natural range key.

```sql
-- When the time comes:
CREATE TABLE orders (...) PARTITION BY RANGE (placed_at);
CREATE TABLE orders_2027_01 PARTITION OF orders
    FOR VALUES FROM ('2027-01-01') TO ('2027-02-01');
```

Benefits: queries filtered by date prune to a single partition; old partitions detach to cold storage in constant time; `VACUUM` works on manageable units. Cost: the partition key must appear in the primary key, and cross-partition queries get slower. Do not do this early.

## 13. The invariants

If any of these is ever false, there is a bug. Each is enforced by a constraint, a test, or both.

1. `inventory_items.quantity_reserved <= quantity_on_hand` — constraint
2. `orders.total = subtotal - discount + shipping + tax` — constraint
3. `orders.refunded_amount <= total_amount` — constraint
4. `payments.amount_refunded <= amount_captured` — constraint
5. `order_items.quantity_fulfilled <= quantity` — constraint
6. `order_items.quantity_returned <= quantity_fulfilled` — constraint
7. One order per checkout session — unique constraint on `checkout_session_id`
8. One payment per provider intent — unique constraint on `(provider, provider_intent_id)`
9. One webhook processed per provider event — unique constraint on `(provider, provider_event_id)`
10. Every order has at least one order item — enforced in the service layer within the creation transaction
11. Every paid order has a succeeded payment — asserted by a nightly reconciliation check
12. Sum of `inventory_movements.quantity_delta` per variant equals `quantity_on_hand` — asserted by a nightly integrity check

Invariants 11 and 12 cannot be expressed as constraints, so they are verified by scheduled jobs that alert on divergence. A ledger that no longer reconciles with its balance is the earliest possible signal that something is quietly wrong.
